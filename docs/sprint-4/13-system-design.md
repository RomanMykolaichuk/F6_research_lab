# 13. Проєктування інформаційних систем як дослідницьких артефактів

## Вимоги та простежуваність
Визначте функціональні вимоги (що система робить) і нефункціональні (якість, затримка, доступність, відтворюваність). Для кожної вимоги задайте критерій прийняття. Вимога «швидко» непридатна без одиниці, навантаження та порога.

| Наукове твердження | Компонент | Перевірка |
|---|---|---|
| Метод зменшує втрати даних | Модуль інтеграції | Еталонні відповідності |
| Метод адаптується до навантаження | Планувальник обчислень | Однакові синтетичні потоки |
| Метод забезпечує пояснюваність | Модуль пояснень | Перевірка відповідності пояснення рішенню |

## Архітектура
Відокремлюйте збирання даних, збереження, обчислювальне ядро, API та інтерфейс. ER-модель описує сутності та обмеження; UML — структуру й поведінку; BPMN — процеси. Обирайте нотацію за питанням, а не за кількістю діаграм.

Прототип повинен дозволяти замінити досліджуваний метод базовим без зміни решти системи. Це полегшує контрольоване порівняння. Імітаційна модель не стає цифровим двійником лише через візуалізацію: необхідно обґрунтувати зв'язок із відповідним реальним об'єктом та механізм актуалізації.

## Дані й API
Зберігайте схему, словник полів, одиниці, походження, правила пропусків та версію набору. API має визначати контракт, валідацію, помилки та ідентифікатор експерименту. Не розміщуйте секрети або дані обмеженого доступу у відкритому репозиторії.

Практикум: побудуйте архітектурну схему власного прототипу та матрицю «твердження — компонент — тест».
